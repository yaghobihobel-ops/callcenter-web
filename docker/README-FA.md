# اجرای Docker همان callcenter-web

این بسته‌بندی همان بک‌اند، پنل‌ها، ویجت، دایال‌پلن و صداهای موجود را استفاده می‌کند؛ پروژه دیگری جایگزین نشده و نصب‌کننده قبلی نیز حفظ شده است. این دستورها روی سرور اجرا نشده‌اند.

## اجزا

- `app`: بک‌اند و پنل‌های فعلی، Node.js 20 مطابق نصب‌کننده موجود.
- `db`: MariaDB 10.11 با حجم دائمی؛ فقط روی `127.0.0.1` میزبان منتشر می‌شود.
- `pbx`: Asterisk 20 بسته Debian Bookworm، همان قالب‌های PJSIP/IVR/صف و صداهای فارسی.
- `turn`: coturn با همان قالب و بازه پورت موجود.
- `nginx`: همان قالب vhost موجود، با TLS و پروکسی پنل و WebSocket.

برای حفظ شنونده loopback بک‌اند و مسیر واقعی RTP، سرویس‌های app/pbx/turn/nginx از شبکه میزبان لینوکس استفاده می‌کنند. این استقرار برای یک VM لینوکسی است، نه Docker Desktop با شبکه متفاوت. دیتابیس در شبکه جداگانه کانتینری است. تغییر منطقی بک‌اند فقط پذیرش `CC_SFTP_PORT` و `CC_SFTP_USER` است تا بازیابی ضبط‌ها از SSH داخلی کانتینر انجام شود؛ پیش‌فرض نصب غیر Docker همان `root:22` باقی مانده است.

## پیش‌نیازها

- Docker Engine و Docker Compose v2 روی لینوکس.
- دامنه و گواهی معتبر HTTPS؛ فایل full chain و کلید خصوصی را فراهم کنید. این بسته certbot یا صدور خودکار گواهی اضافه نمی‌کند. گواهی self-signed برای میکروفون مرورگر کاربران مناسب نیست.
- DNS دامنه به آدرس عمومی سرور برسد. اگر Cloudflare استفاده می‌شود، رکورد این سرویس را **DNS only** کنید؛ پروکسی HTTP کلادفلر مسیر RTP/TURN را عبور نمی‌دهد.
- پورت‌های خالی میزبان: `80,443/tcp`، `3478/tcp+udp`، `10000-10199/udp`، `49160-49200/udp`.
- پورت‌های loopback میزبان: `3006`، `5038`، `8088`، `2222` و `3306`. پورت SSH خود VM (`22`) دست‌نخورده می‌ماند. `APP_PORT` و `DB_PORT` قابل تغییرند؛ سایر پورت‌ها مطابق سورس ثابت‌اند.
- دسترسی به Docker Hub و registry npm هنگام build. محدودیت شبکه/تحریم این دسترسی را جداگانه بررسی کنید.

وضعیت پورت‌ها و نشانی اینترفیس را فقط بررسی کنید:

```bash
sudo ss -lntup
ip -4 route get 1.1.1.1
```

## آماده‌سازی و اجرا

از ریشه ریپو:

```bash
chmod +x docker/init.sh
./docker/init.sh
```

اسکریپت فقط `.env` را با رمزهای تصادفی می‌سازد و فایل موجود را بازنویسی نمی‌کند. سپس `.env` را ویرایش کنید:

- `CC_DOMAIN`: نام واقعی، مثلاً `call.example.com`.
- `PUBLIC_IP`: IP عمومی قابل دسترسی مشتری، نه IP پروکسی Cloudflare.
- `CC_HOST_IP`: IP اختصاص‌یافته به اینترفیس VM. در VM با IP عمومی مستقیم، معمولاً برابر `PUBLIC_IP` است؛ پشت NAT، آدرس داخلی VM است.
- `TLS_CERT_FILE` و `TLS_KEY_FILE`: مسیر گواهی و کلید؛ مسیر نسبی از ریشه ریپو است.
- شماره پشتیبانی و برند را با اطلاعات واقعی جایگزین کنید.

مقادیر نمونه `example.com` و `192.0.2.10` واقعی نیستند. فایل‌های پیش‌فرض گواهی را در `docker/certs/fullchain.pem` و `docker/certs/privkey.pem` قرار دهید یا مسیرشان را در `.env` عوض کنید. کلید خصوصی باید برای خواندن توسط root کانتینر nginx قابل خواندن باشد. برچسب SELinux برای این دو bind mount در Compose تنظیم شده است.

ابتدا فقط اعتبارسنجی کنید، سپس در صورت آماده بودن سرور اجرا کنید:

```bash
docker compose config --quiet
docker compose build
docker compose up -d
docker compose ps
docker compose logs --tail=100 app pbx turn nginx
```

نشانی‌ها: `/admin/`، `/operator/` و `/widget.js` روی دامنه شما. کاربرهای اولیه همان رفتار سورس را دارند (`admin` و `operator`)؛ رمزهای پیش‌فرض اولیه در سورس عمومی‌اند، پس **پیش از انتشار سرویس، رمز هر دو حساب را از پنل عوض کنید**. متغیر ساختگیِ رمز مدیر به Compose اضافه نشده، چون بک‌اند فعلی آن را مصرف نمی‌کند.

## فایروال و شبکه

فقط پورت‌های عمومی فهرست بالا را در فایروال VM و فایروال لبه/مودم باز یا فوروارد کنید. پورت‌های دیتابیس، AMI، WS خام، API و SFTP ضبط‌ها نباید عمومی شوند. شنونده‌های داخلی به loopback محدود شده‌اند. باز کردن پورت‌ها یا تغییر SELinux در این مرحله انجام نشده است.

مسیر رسانه همچون نصب اصلی است:

`مرورگر → WSS روی nginx → Asterisk` و `RTP/ICE → Asterisk/coturn`.

داخلی‌های 1000 تا 1005، شماره‌گیری 200، صف support و نظرسنجی حفظ شده‌اند. اتصال CRM خارجی اختیاری است؛ اتصال پیش‌فرض SQLite به فایل سایت firuzo در VM تازه وجود ندارد. می‌توانید اتصال MySQL را در تنظیمات پنل پیکربندی کنید. برای فایل SQLite خارجی باید مسیر آن را با یک mount فقط‌خواندنی در override کانتینر app در دسترس قرار دهید. این بسته هیچ خط تلفن یا SIP trunk تازه‌ای اضافه نمی‌کند.

## ضبط‌ها و داده‌ها

Asterisk در `asterisk_spool` ضبط می‌کند. همان流れ SFTP قبلی از یک SSH داخلی فقط‌خواندنی روی `127.0.0.1:2222` فایل را به `recording_cache` منتقل می‌کند. حساب `ccrec` فقط به پوشه ضبط‌ها دسترسی دارد؛ کلید آن در حجم `recording_keys` ساخته می‌شود و به authorized_keys خود VM اضافه نمی‌شود.

حجم‌های `db_data`، `asterisk_spool`، `recording_cache`، `asterisk_state`، `asterisk_logs`، `recording_keys` و `pbx_ssh` با restart معمولی حفظ می‌شوند. دستور `docker compose down --volumes` داده‌ها را پاک می‌کند؛ برای توقف معمولی از آن استفاده نکنید. پشتیبان‌گیری از دیتابیس و ضبط‌ها همچنان لازم است.

## حدود اعتبارسنجی

در آماده‌سازی این تغییر، بررسی ایستا انجام شد: ساختار YAML و وابستگی سرویس‌های Compose، ShellCheck اسکریپت‌ها، syntax بک‌اند، اعتبارسنج Asterisk موجود، رندر قالب‌های PBX/TURN/nginx، حالت NAT و IP مستقیم، branding ویجت و ساختار supervisor. نصب قفل npm با Node 20 بدون اجرای اسکریپت‌های نصب نیز بررسی شد.

در محیط آماده‌سازی، Docker daemon در دسترس نبود و دریافت باینری Compose هم با محدودیت شبکه مواجه شد؛ بنابراین `docker compose config`، build ایمیج‌ها و تماس صوتی واقعی تا زمان اجرا روی VM تأیید نشده‌اند. «Dockerized» در اینجا به معنی آماده‌سازی بسته استقرار است، نه ادعای دیپلوی یا تست صوت زنده.
